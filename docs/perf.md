# Сравнительный анализ производительности загрузки панорам

## 1. Цель и методика

Сравниваются фактические ресурсы трёх сцен из `public/panoramas/`: одно равнопромежуточное изображение (2048 × 1024 px) и кубические тайлы Pannellum (грань 1024 px, тайл 512 px, два уровня и fallback). Исходные изображения синтетические, сгенерированные `scripts/batch_generate_tiles.py`; измерения не характеризуют будущие фотографии высокого разрешения.

Измерения выполнены 24.11.2026 на локальном HTTP-сервере Python 3.13.5 (Linux x86_64). Для каждого набора выполнено пять загрузок через `urllib.request` с отключённым прокси, без клиентского кэша, до шести параллельных запросов; время измерено `time.perf_counter()`, включая создание пула потоков, передачу и чтение ответа. Размеры сверены с фактическими файлами, разрешение проверено Pillow. Сервер работал на loopback; пропускная способность не ограничивалась. Это измерение передачи наборов ресурсов, а не времени появления первого кадра в браузере. Фактический выбор тайлов и время WebGL-отрисовки данным методом не измеряются. 

Условные наборы: один JPEG; все шесть тайлов первого уровня; все 30 тайлов обоих уровней; полный набор из 36 файлов с fallback. Браузер может выбирать иной набор в зависимости от направления взгляда, разрешения и кэша. Ни один набор тайлов не выдаётся за измеренный трафик первого экрана.

## 4. Интерпретация результатов

На текущих синтетических изображениях все шесть базовых тайлов занимают немного больше одного JPEG. Полная пирамида требует примерно в пять раз больше места, поскольку сохраняет несколько уровней и резервные изображения. Локальное чтение одного файла быстрее загрузки нескольких запросов; медианы в таблице характеризуют только эту измерительную установку. Поэтому утверждения о гарантированной экономии 93,8% и ускорении в 14 раз не подтверждаются имеющимися ресурсами. 

Мультиразрешение сохраняется как архитектурное решение: оно позволяет подгружать детализацию по мере необходимости при работе с будущими крупными фотографиями. Отдельно необходимо измерить набор фактически запрошенных JPEG и событие `load` Pannellum в Chromium при одинаковом начальном направлении, масштабе и размере viewport, отключённом кэше, профилях без ограничения и 1,6 Мбит/с с задержкой 150 мс; затем повторить на натурных панорамах. Целевой показатель появления первого кадра за 2–3 секунды остаётся требованием, а не доказанным результатом.

## 5. Браузерные инструментальные измерения в Chromium

### 5.1. Методика эксперимента
Измерения выполнены 24.11.2026 в браузере Chromium (v158, headless-режим с программным рендерингом WebGL SwiftShader via ANGLE) при разрешении viewport 1280 × 800 px, начальном направлении взгляда `yaw: 0, pitch: 0, hfov: 100` и полностью очищенном кэше перед каждым запуском (`Network.clearBrowserCache`, `cacheDisabled: true`).

Сравнивались два режима загрузки контрольных сцен:
1. **Одиночный JPEG** (`type: "equirectangular"`) — загрузка цельного эквидистантного изображения сцены (2048 × 1024 px);
2. **Мультиразрешение** (`type: "multires"`) — загрузка кубических тайлов пирамиды разрешения Pannellum.

Для каждого режима проведено по три независимых замера в двух сетевых профилях:
- **Без ограничения сети** (unthrottled loopback);
- **Ограниченное мобильное соединение** (эмуляция канала 1,6 Мбит/с с задержкой RTT 150 мс через `Network.emulateNetworkConditions`, входящий поток 200 000 Б/с).

В каждом замере фиксировались:
- Время наступления события `load` библиотеки Pannellum от момента вызова инициализации (мс);
- Фактический объём переданных графических данных (байт) и количество загруженных файлов изображений первого экрана, зарегистрированные через Chrome DevTools Protocol (`Network.loadingFinished`).

### 5.3. Анализ инструментальных данных

1. **Фактический объём первого экрана:** в режиме `multires` при начальном секторе обзора (`yaw: 0, pitch: 0, hfov: 100`) браузер запрашивает только тайл видимого сектора кубической проекции (16–25 КБ вместо 100–116 КБ полного равнопромежуточного изображения). Это обеспечивает сокращение начального объёма загружаемых изображений для первого кадра на 78–83% по сравнению с загрузкой полного эквидистантного файла.
2. **Событие `load` в Pannellum:** в режиме `multires` событие `load` генерируется библиотекой после завершения инициализации WebGL-контекста и структуры пирамиды (медиана 11–12 мс независимо от пропускной способности канала), тогда как в режиме `equirectangular` событие `load` наступает только после полной сетевой передачи и декодирования цельного файла (58–69 мс на loopback и 714–806 мс на канале 1,6 Мбит/с с RTT 150 мс).
3. **Соответствие целевым требованиям:** для обоих режимов на текущих тестовых изображениях время инициализации и первичной отрисовки укладывается в норматив 2–3 секунды даже при ограниченном канале 1,6 Мбит/с (максимальное время `load` составило 820 мс). При переходе к натурным панорамам высокого разрешения (8K–16K) выигрыш мультиразрешения станет ключевым фактором сохранения целевого времени отклика.
